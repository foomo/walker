# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Walker crawls a website and collects performance, SEO and broken-link data. It serves the results through a minimal web UI (`/`, `/status`, `/reports/...`) and as Prometheus metrics (`/metrics`). Aggressive settings (high `concurrency`) can take a target site down, so keep that in mind when you run it against real hosts.

## Commands

```sh
go build ./...                                   # build everything
go run ./cmd/walker path/to/config.yaml          # run the crawler + web UI (default addr :3001), -exit-on-stdin-close for the macOS app
go run ./cmd/validator schema-root group https://host/page   # validate one page, exit 3 on error findings
go test ./...                                    # all tests
go test ./config -run TestLoad                   # single test
go test ./htmlschema/... -v                      # syntax, lint, rules + golden tests of the SPEC.md examples
go install ./cmd/htmlschema-lsp                  # language server for schema files, extensions in editors/zed-htmlschema and editors/vscode-htmlschema
go run ./cmd/configvalidator config.yaml         # validate a walker config: unknown keys, types, schema root - exit 3 on errors
go run ./cmd/demo                                # demo shop on :8080 (reads templates, css, catalogue from source on every request), schema in htmlschema/demo/schema, group header x-next-js-app
```

`mise.toml` pins Go and `gotsrpc` (keep it in sync with `go.mod`) and wraps the commands above as tasks (`mise tasks`; `mise run generate` regenerates the Go proxy and the Swift client; `goswiftrpc` is pre-alpha without mise support, so `generate:swift` runs `go install github.com/foomo/goswiftrpc/cmd/goswiftrpc@latest` first). The `Makefile` holds only ad-hoc deploy targets (cross-compile, then scp to a stage host); it isn't a build system. The `Dockerfile` builds both binaries and bakes in `cmd/walker/config-example.yaml`.

## Configuration

`config.Load` parses the YAML into an internal `config` struct and then normalizes it into the public `config.Config`:
- `target` can be a plain URL string or a map `{baseurl, paths: [...]}`. If `paths` is missing, the path in the URL becomes the single start path and `BaseURL` keeps only the scheme and host.
- Defaults: `concurrency: 2`, `addr: ":3001"`, `usecookies: true`, `agent: foomo-walker`.
- `interval` / `offset` (durations): wall-clock-aligned scrape schedule, see `schedule.go`. `0` means restart immediately.
- Other keys: `ignore` (path prefixes), `ignorequerieswith`, `ignoreallqueries`, `ignorerobots`, `depth`, `paging`, `groupheader`, `schemaroot`.

Most `cmd/walker/*.yaml` files are local, site-specific configs and are usually untracked. `config.Validate` checks a config file with line numbers (`Load` silently ignores unknown keys), `config.ReadForm`/`WriteForm` turn it into a form and back while keeping comments and unknown keys.

## Architecture

**Actor-style core (`walker.go`, `scrapeloop.go`).** `NewWalker` starts one goroutine, `scrapeloop`, which owns all crawl state: the job map, results and the client pool. Public methods (`Walk`, `Stop`, `Restart`, `GetStatus`, `GetStatuses`) never touch that state directly. Each one sends a request on a channel and waits for the reply on that same channel. Keep it this way: new features that read or change crawl state should add a channel case to the `select` in `scrapeloop`, not shared fields or mutexes. `GetStatuses()` returns the last completed cycle and the running one (`nil` while idle between scheduled cycles), and the reports render both. `GetStatus()` returns the current cycle. `Restart()` starts a new cycle right away (service `RestartScrape`, the "New Scrape" button of the overview); requests still in flight of an aborted cycle free their clients, their results are dropped (`dispatched` remembers the cycle of each busy client).

**Scraping (`scrape.go`).** `scrapeloop` hands each job a free `poolClient` from `clientPool` (one `http.Client` per unit of concurrency, optional cookie jar, TLS verification disabled, redirect chain recorded via request context) and calls `scrape` in its own goroutine. Results come back over `chanResult`. `scrape` parses the HTML with goquery and runs `extract.go`, which pulls out title, description, h1, canonical and JSON-LD into `vo.Structure`. It also collects links (including links inside `<noscript>`) and, if configured, runs schema validation.

**Extension hooks.** `Walk`/`NewService` take four optional funcs (`cmd/walker` passes `nil` for all of them), so library users can customize crawling:
- `LinkListFilterFunc`: which links to follow. The default lives in `filterscrapelinks.go`; it normalizes links, stays on the host, and applies the ignore/query/depth/paging rules plus robots.txt (`robotstxt.go`).
- `ScrapeFunc`: extracts custom data from the response.
- `ValidationFunc`: produces `vo.Validations` from the structure and the scrape data.
- `ScrapeResultModifierFunc`: post-processes each result.

**htmlschema.** The language is specified in `htmlschema/SPEC.md`, whose worked examples (section 14, demo shop pages) are the golden tests in `examples_test.go`. Change spec and examples together. `LoadRoot(schemaroot)` reads every `.html` below the root and returns all problems as `LintErrors`. Only `groups/<group>.html` and `default.html` (the fallback) are fixed locations, and the rest is shared via `val:include` and `val:comp`. Files with a `val:component` root are recognized components. `Root.Validate(group, html)` returns a `Report`: findings (severity + penalty), a score tree with a computed maximum, and per-component summaries. Score and penalty are never combined. The pipeline: `syntax.go` (tokenizer tree builder, no HTML5 recovery) → `compile.go` (includes, comps, wildcards flattened into per-element `skip` selectors, lint) → `score.go` (static max) → `page.go` (exclusion set, component recognition, locators) → `match.go`/`validate.go`/`ld.go`. A page's group comes from the response header named by `groupheader`. The demo shop is the example: `htmlschema/demo/schema` holds its schema tree, `htmlschema/demo/server` renders the pages (`server.NewHandler`, group header `x-next-js-app`); the golden tests and the walker and service tests render pages through that handler, without a port. Editor support: `cmd/htmlschema-lsp` (completion and hover from `htmlschema.Vocabulary()`, which is derived from the compiler's rule tables, plus lint diagnostics via `LoadRootOverlay` with the unsaved buffers), registered in Zed by the dev extension `editors/zed-htmlschema` and in VS Code by `editors/vscode-htmlschema` (plain JavaScript client on `vscode-languageclient`, no build step; it resolves the binary also in go's bin directories). Both only start the binary - server features belong in `cmd/htmlschema-lsp`.

**semanticscrape.** `semanticscrape.ExtractDocument(html, options)` returns the gist of a page: `Lang`, `Title` and `Description` from the head and `Body`, the outline of the body. The outline holds the landmarks (the visible `main` or `role="main"`, the page's `header` and `footer`, `nav`s with their `Links`), articles, sections, asides and headings in document order; all other elements are transparent, hidden subtrees (`hidden`, `aria-hidden="true"`) are left out. A header or footer inside an article, aside, main, nav or section belongs to that element and is transparent. ARIA roles count as the elements they stand for, headings carry their accessible name (`Text`), containers the name their author gave them (`Label`). Pages without semantic containers fall back to divs: a div with a heading of its own next to other content is a container, wrapper chains collapse to one div whose selector is the tightest box that still holds the whole unit. `Document.Main()` finds the main in the outline; `Body` is never nil (`[]` on the wire). `Options{Content: true}` (`content.go`) adds the content of the containers between their elements in reading order, in a separate pass over the finished tree, so it never changes the structure: `text` blocks with the links in them, `img` (alt as `Text`, `Src` with lazy loading fallbacks, an image link's link in `Links`), `figure` (caption as `Text`), lists (`ul`/`ol`/`role="list"` with `li`, `dl` with `dt`/`dd`; an item's leading text is its `Text`, the rest its children; empty items and lists are left out), tables (caption as `Text`, `tr` rows of `th`/`td` cells with text and links; lists and tables around outline elements and `role="presentation"` tables stay transparent), and headings get their teaser link; navs get no content, controls and svg are none. The extractor keeps each element's html node in the unexported `node` field during the run and clears it at the end. Tests run the fixtures in `semanticscrape/test_data`: the sourdough page in three markups (semantic, div soup, ARIA) must give the same outline, the reduced and anonymized news homepage has golden outlines with and without content (`go test ./semanticscrape -update`). The service exposes it as `GetSemanticDocument(targetURL, html, content)` (`semanticservice.go`): with html it extracts that, without it fetches the http(s) url like `ValidateSchema` does.

**Reports (`reports/`).** Each report renders plain text/HTML from a `vo.Status`, and `reports.GetReportHandler(basePath)` routes between them. To add a report, register it in `reports.go`, both in the handler and in `GetReportHandlerMenuHTML`.

**Service API and macOS app.** `Service` (`serviceinterface.go`, implemented by the private `service` in `service.go`, `NewService` returns it and its `*Walker`) is exposed via gotsrpc: `gotsrpc gotsrpc.yaml` (gotsrpc v3, as in `go.mod`) generates the Go HTTP proxy (`gotsrpc_gen.go`, mounted on `/service` in `cmd/walker`), `goswiftrpc generate goswiftrpc.yaml` the Swift client in `macos/Walker/Generated/`. Regenerate both after changing `Service` or any type it returns. Never edit `*_gen.go` or `macos/Walker/Generated/*.swift` by hand. `macos/Walker.xcodeproj` is a SwiftUI app (macOS 26, Swift 6) that compiles `macos/Walker/` (including the generated client) as one synchronized folder, so new files need no project edits. Constraints that come from the generated Swift code:
- Each mapped Go package is a Swift namespace (`WalkerVO`, `HTMLSchemaVO`, `SemanticScrapeVO`, `Walker` for the root package with `Walker.ServiceClient`, `GoTime`), so the app always writes qualified names (`WalkerVO.ScrapeResult`). Extensions too: an unqualified `extension X` no longer finds the generated type.
- A zero `time.Time` is encoded as `null`, but a value `time.Time` becomes a non-optional `Date`. Use `*time.Time` for timestamps that can be unset (see `vo.ScrapeSummary`).
- go's `time.Duration` (nanoseconds) is `GoTime.Duration`; a bare `Duration` is `Swift.Duration`.
- The app has no graph view for now - the 3D graph was removed, the Go side (`GetGraph`, `GetPageGraph`, `GetPageFolderLinks`, `GetFolderPages`) stays and the generated Swift client still has those calls.
- The schema developer window (`SchemaDevView`, `SchemaDevModel`, `SchemaWebView`) iterates on an html schema against a live page. It calls `GetSchemaRoot`/`ValidateSchema`/`GetSchemaRootVersion` (`schemaservice.go`; the app polls the version every second and validates again when a schema file changes), which load the schema root from a path on the server (client and server share a file system) and return an `htmlschema.TraceNode` tree (`Root.Trace`). Selecting a node highlights its locators in the WKWebView. "Load Config" takes the site (base url + first path) and the schema root (resolved against the config's directory) of a local config (`SchemaDevModel.load`); the window of a local server starts with its own config. The tree (`SchemaTreeView`) writes rules as plain-language chips, marks elements from other schema files (`Source`) and wildcards (`TraceNode.Via`), and shows the details of the selected node inline - neutral selection, a click on the selected row toggles the details, keyboard navigation is its own (List without selection binding). Source references open the editor chosen in the settings at the line (`SourceLink`, `zed://file…`, `vscode://file…`). The middle column (`PageDataView`) shows a link preview from the OpenGraph data (`OpenGraphView`), the head and the JSON-LD of the validated html (`htmlschema.ExtractPageData`, same locators as the trace), linked with the tree in both directions. The right column (`OutlinePane`, toolbar toggle, hidden by default) shows the semantic outline of the page from the same source as the validation - for "Rendered" the DOM snapshot goes to `GetSemanticDocument` as html, so selectors match the web view; it reloads with the page (`SchemaDevModel.pageVersion`), the source and the content switch, not with schema edits, and hovering highlights in the page via `SchemaHighlighter.highlight(locators:color:)`.
- The app is **not sandboxed** (hardened runtime only): local walkers read configs and schema roots by path. The "helpers" run script phase builds `cmd/walker` and `cmd/configvalidator` into `Contents/Helpers` (with the Go pinned in `mise.toml`, resolved via `mise which go` with `GOTOOLCHAIN=local` - the build fails if mise is missing or `mise trust && mise install` hasn't run; target `ENABLE_USER_SCRIPT_SANDBOXING = NO`, go needs its module cache).
- Configs are edited only in the main window, in the overview of a local server: `LocalConfigForm` is the config form (`ConfigFormView`, fields with notes on the resulting crawl behaviour - keep them in sync with the Go side) with the walker's state on top. It saves to the file right away and rereads it when it changes on disk. Its yaml backend is the `configvalidator` helper; `ConfigTool` talks to it over stdin/stdout JSON.
- Local walkers: a `Server` with a `configPath` is a local config (sidebar section "Local"), its `baseURL` follows the config's `addr` (`ServerStore.refreshLocal`, not while its walker runs). `LocalWalkers` (owned by the `AppDelegate`, which stops them on quit) runs the walker helper per config with `-exit-on-stdin-close`, in the config's directory, and keeps state and log (`LocalWalkers.logLines`, a setting, default 10000 lines). Local servers get the normal `ServerDetailView`; their `OverviewView` puts the scrape cards above the log (`LocalWalkerLogPane`) and the config form beside them.
- Live metrics (top of the Performance view, `LiveMetrics`, `LiveMetricsView`): the `AppDelegate` (owner of `ServerStore` and `LocalWalkers`) runs `ServerStore.sampleMetrics` for the app's lifetime: every refresh interval it reads the `/metrics` of all servers in parallel (local ones only while running, 5 s timeout) (`PromText` parses the text format) and keeps the charted series for 30 minutes in memory - a local debugging tool. Each `MetricsChart` is evaluated locally (rate, gauge, histogram quantile over bucket increases) and carries the equivalent PromQL, so a Prometheus server backend can answer the same charts later. Charts use one axis each; new metrics need a `kept` entry, a chart case and its PromQL.
- The result inspector (`ResultSections`, shared by the results, folder and broken link inspectors) shows the semantic outline of the whole page (`SemanticOutlineSection`, `SemanticOutline`) instead of the scraped headings - landmarks tinted, navs collapsed with their links, a "Content" switch (`outlineShowsContent`) adds texts, images with thumbnails, figures, lists with markers and tables as grids: the server fetches the live page via `GetSemanticDocument`, the loader comes from the environment (`semanticDocumentLoader`, set in `ServerDetailView`). Hovering an element highlights it in the preview by its selector (`PreviewController.highlight`), headings the selector misses in the live DOM are found by level and text. Title, description, canonical and robots still come from the scrape result's `Structure`.
- The app target must not use `MainActor` default isolation (it would isolate the generated `Codable` conformances). App model classes are `@MainActor` explicitly.

**Logging.** Log messages go through `log/slog` with attributes (`slog.Info("scrape cycle completed", "pages", n)`), never `fmt.Print`/`log.Print`. `cmd/walker` sets the default logger: `-log-level debug|info|warn|error`, `-log-format text|json`, text on stderr by default. `fmt` is only for program output: CLI results and usage, reports, `configvalidator`'s stderr (the app shows it as is). The app's log view parses the slog text lines (`SlogEntry`), so keep walker's default format text.

**Other pieces.** `service.go` wraps the Walker with filtering and paging over results. `metrics.go` gives each Walker its own Prometheus registry (`MetricsHandler()`). The loop only updates the few true counters. All per-scrape metrics come from a collector that derives them from `GetStatuses()` at scrape time, once per view, with `scrape="current"|"complete"`. Add new per-scrape metrics there, not as state in `scrapeloop`. `validationmetrics.go` aggregates schema validation reports for it. `vo/` holds the shared value objects (`Status`, `ScrapeResult`, `Structure`, `Validations`).
