# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Walker crawls a website and collects performance, SEO and broken-link data. It serves the results through a minimal web UI (`/`, `/status`, `/reports/...`) and as Prometheus metrics (`/metrics`). Aggressive settings (high `concurrency`) can take a target site down, so keep that in mind when you run it against real hosts.

## Layout

A monorepo. All Go code is one module in `go/` (module path `github.com/foomo/walker/go`, release tags `go/vX.Y.Z`): binaries in `go/cmd/`, every package in `go/internal/` - there is no public Go API. Next to it: the macOS app (`macos/`), the editor extensions for the semantic shape language server (`editors/`), `mise.toml`, `Dockerfile` and the `Makefile` at the root. Package paths below are relative to `go/internal/` unless they start with `go/`, `macos/` or `editors/`. The packages: `crawler` (the engine), `service` (its gotsrpc api), `metrics`, `reports`, `config`, `semanticshape`, `semanticscrape`, `vo` (shared value objects) and `demoshop` (the demo shop and its shape, the test fixture of all of them). Dependencies point one way: `cmd/walker` wires `crawler`, `metrics`, `service` and `reports`; `service` and `metrics` use the crawler only through its public methods; `crawler` imports neither.

## Commands

Run Go commands in `go/` (or `go -C go …` from the root); the mise tasks do that themselves.

```sh
go build ./...                                   # build everything
go run ./cmd/walker path/to/config.yaml          # run the crawler + web UI (default addr :3001), -exit-on-stdin-close for the macOS app
go run ./cmd/validator shape-root group https://host/page   # validate one page, exit 3 on error findings
go test ./...                                    # all tests
go test ./internal/config -run TestLoad          # single test
go test ./internal/semanticshape/... -v          # syntax, lint, rules + golden tests of the SPEC.md examples
go install ./cmd/semanticshape-lsp               # language server for shape files, extensions in editors/zed-semanticshape and editors/vscode-semanticshape
go run ./cmd/configvalidator config.yaml         # validate a walker config: unknown keys, types, shape root - exit 3 on errors
go run ./cmd/demo                                # demo shop on :8080 (reads templates, css, catalogue from source on every request), shapes in internal/demoshop/shapes, group header x-next-js-app
```

`mise.toml` pins Go and `gotsrpc` (keep it in sync with `go/go.mod`) and wraps the commands above as tasks that run in `go/` (`mise tasks`; `mise run editors` installs the language server and builds both editor extensions, `editors:zed` compiles the Zed extension to wasm, `editors:vscode` packages the `.vsix` with the servers of `editors:vscode:server` (macOS, Linux, Windows), `editors:vscode:install` installs it; `mise run generate` regenerates the Go proxy and the Swift client; `goswiftrpc` is pre-alpha without mise support, so `generate:swift` runs `go install github.com/foomo/goswiftrpc/cmd/goswiftrpc@latest` first). The generator configs `go/gotsrpc.yaml` and `go/goswiftrpc.yaml` are run from `go/`; the Swift namespaces are fixed there, independent of the Go package paths. The `Makefile` holds only ad-hoc deploy targets (cross-compile, then scp to a stage host); it isn't a build system. The `Dockerfile` (build context: the repo root) builds both binaries and bakes in `go/cmd/walker/config-example.yaml` with the demo shapes, in the repository's layout under `/app` (the config's `shaperoot` is relative).

## Configuration

`config.Load` parses the YAML into an internal `config` struct and then normalizes it into the public `config.Config`:
- `target` can be a plain URL string or a map `{baseurl, paths: [...]}`. If `paths` is missing, the path in the URL becomes the single start path and `BaseURL` keeps only the scheme and host.
- Defaults: `concurrency: 2`, `addr: ":3001"`, `usecookies: true`, `agent: foomo-walker`.
- `interval` / `offset` (durations): wall-clock-aligned scrape schedule, see `crawler/schedule.go`. `0` means restart immediately.
- Other keys: `ignore` (path prefixes), `ignorequerieswith`, `ignoreallqueries`, `ignorerobots`, `depth`, `paging`, `groupheader`, `schemaroot`.

Most `go/cmd/walker/*.yaml` files are local, site-specific configs and are usually untracked. `config.Validate` checks a config file with line numbers (`Load` silently ignores unknown keys), `config.ReadForm`/`WriteForm` turn it into a form and back while keeping comments and unknown keys.

## Architecture

**Actor-style core (`crawler`: `walker.go`, `scrapeloop.go`).** `crawler.New(observer)` starts one goroutine, `scrapeloop`, which owns all crawl state: the job map, results and the client pool. Public methods (`Walk`, `Stop`, `Restart`, `GetStatus`, `GetStatuses`) never touch that state directly. Each one sends a request on a channel and waits for the reply on that same channel. Keep it this way: new features that read or change crawl state should add a channel case to the `select` in `scrapeloop`, not shared fields or mutexes. `GetStatuses()` returns the last completed cycle and the running one (`nil` while idle between scheduled cycles), and the reports render both. `GetStatus()` returns the current cycle. `Restart()` starts a new cycle right away (service `RestartScrape`, the "New Scrape" button of the overview); requests still in flight of an aborted cycle free their clients, their results are dropped (`dispatched` remembers the cycle of each busy client).

**Scraping (`crawler/scrape.go`).** `scrapeloop` hands each job a free `poolClient` from `clientPool` (one `http.Client` per unit of concurrency, optional cookie jar, TLS verification disabled, redirect chain recorded via request context) and calls `scrape` in its own goroutine. Results come back over `chanResult`. `scrape` parses the HTML with goquery and runs `extract.go`, which pulls out title, description, h1, canonical and JSON-LD into `vo.Structure`. It also collects links (including links inside `<noscript>`) and, if configured, runs shape validation.

**Extension hooks.** `Walker.Walk` takes four optional funcs (`cmd/walker` passes `nil` for all of them), so crawling can be customized:
- `LinkListFilterFunc`: which links to follow. The default lives in `filterscrapelinks.go`; it normalizes links, stays on the host, and applies the ignore/query/depth/paging rules plus robots.txt (`robotstxt.go`).
- `ScrapeFunc`: extracts custom data from the response.
- `ValidationFunc`: produces `vo.Validations` from the structure and the scrape data.
- `ScrapeResultModifierFunc`: post-processes each result.

**semanticshape.** Semantic shapes (formerly htmlschema) describe the semantic structure a page of a group must have, as html files named `*.semanticshape.html` (`semanticshape.FileSuffix`) - every other file below a root is ignored, a root with only plain `.html` files fails with a lint error that names the rename. The directory of the shapes is the shape root, config key `shaperoot` - always written relative to the config file (`ConfigTool.relativePath` in the app: the Shapes section, the config form's chooser and a typed absolute path once the field loses focus) and resolved against it by `config.Get` and `config.Validate` (`schemaroot` is still accepted as its old name: `config.Load` maps it, `config.Validate` notes it, `WriteForm` renames the key in place). The app's settings keys are `shapeDev…`; `SettingsMigration` (run in `AppDelegate.init`, before any view reads them) moves the values of the old `schemaDev…` keys once. The language is specified in `semanticshape/SPEC.md`, whose worked examples (section 14, demo shop pages) are the golden tests in `examples_test.go`. Change spec and examples together. `LoadRoot(shaperoot)` reads every `*.semanticshape.html` below the root and returns all problems as `LintErrors`. Only `groups/<group>.semanticshape.html` and `default.semanticshape.html` (the fallback) are fixed locations, and the rest is shared via `val:include` and `val:comp`. Files with a `val:component` root are recognized components. `Root.Validate(group, html)` returns a `Report`: findings (severity + penalty), a score tree with a computed maximum, and per-component summaries. Score and penalty are never combined. The pipeline: `syntax.go` (tokenizer tree builder, no HTML5 recovery) → `compile.go` (includes, comps, wildcards flattened into per-element `skip` selectors, lint) → `score.go` (static max) → `page.go` (exclusion set, component recognition, locators) → `match.go`/`validate.go`/`ld.go`. A page's group comes from the response header named by `groupheader`. The demo shop is the example: package `demoshop` renders the pages (`demoshop.NewHandler`, group header `x-next-js-app`), `demoshop/shapes` holds its shape tree (`demoshop.ShapesDir()`); the golden tests and the crawler and service tests render pages through that handler, without a port. Editor support: `go/cmd/semanticshape-lsp` (only for `*.semanticshape.html` files; completion and hover from `semanticshape.Vocabulary()`, which is derived from the compiler's rule tables, plus lint diagnostics via `LoadRootOverlay` with the unsaved buffers), registered in Zed by the dev extension `editors/zed-semanticshape` and in VS Code by `editors/vscode-semanticshape` (plain JavaScript client on `vscode-languageclient`; it bundles the server - `mise run editors:vscode:server` cross-compiles it into `server/<process.platform>-<process.arch>`, gitignored - and falls back to the `PATH` and go's bin directories; `semanticshape.serverPath` overrides both). Both only start the binary - server features belong in `go/cmd/semanticshape-lsp`.

**semanticscrape.** `semanticscrape.ExtractDocument(html, options)` returns the gist of a page: `Lang`, `Title` and `Description` from the head and `Body`, the outline of the body. The outline holds the landmarks (the visible `main` or `role="main"`, the page's `header` and `footer`, `nav`s with their `Links`), articles, sections, asides and headings in document order; all other elements are transparent, hidden subtrees (`hidden`, `aria-hidden="true"`) are left out. A header or footer inside an article, aside, main, nav or section belongs to that element and is transparent. ARIA roles count as the elements they stand for, headings carry their accessible name (`Text`), containers the name their author gave them (`Label`). Pages without semantic containers fall back to divs: a div with a heading of its own next to other content is a container, wrapper chains collapse to one div whose selector is the tightest box that still holds the whole unit. `Document.Main()` finds the main in the outline; `Body` is never nil (`[]` on the wire). `Options{Content: true}` (`content.go`) adds the content of the containers between their elements in reading order, in a separate pass over the finished tree, so it never changes the structure: `text` blocks with the links in them, `img` (alt as `Text`, `Src` with lazy loading fallbacks, an image link's link in `Links`), `figure` (caption as `Text`), lists (`ul`/`ol`/`role="list"` with `li`, `dl` with `dt`/`dd`; an item's leading text is its `Text`, the rest its children; empty items and lists are left out), tables (caption as `Text`, `tr` rows of `th`/`td` cells with text and links; lists and tables around outline elements and `role="presentation"` tables stay transparent), and headings get their teaser link; navs get no content, controls and svg are none. The extractor keeps each element's html node in the unexported `node` field during the run and clears it at the end. Tests run the fixtures in `semanticscrape/test_data`: the sourdough page in three markups (semantic, div soup, ARIA) must give the same outline, the reduced and anonymized news homepage has golden outlines with and without content (`go test ./semanticscrape -update`). The service exposes it as `GetSemanticDocument(targetURL, html, content)` (`service/semanticservice.go`): with html it extracts that, without it fetches the http(s) url like `ValidateShape` does.

**Reports (`reports/`).** Each report renders plain text/HTML from a `vo.Status`, and `reports.GetReportHandler(basePath)` routes between them; `reports.PrintStatus` is the `/status` page. To add a report, register it in `reports.go`, both in the handler and in `GetReportHandlerMenuHTML`.

**Service API and macOS app.** `service.Service` (`service/serviceinterface.go`, implemented by the private `service` in `service/service.go`, `service.New(walker, conf)` - it doesn't start the walk) is exposed via gotsrpc: `gotsrpc gotsrpc.yaml` (gotsrpc v3, as in `go/go.mod`) generates the Go HTTP proxy (`service/gotsrpc_gen.go`, mounted on `/service` in `go/cmd/walker`), `goswiftrpc generate goswiftrpc.yaml` the Swift client in `macos/Walker/Generated/`. Regenerate both after changing `Service` or any type it returns. Never edit `*_gen.go` or `macos/Walker/Generated/*.swift` by hand. `macos/Walker.xcodeproj` is a SwiftUI app (macOS 26, Swift 6) that compiles `macos/Walker/` (including the generated client) as one synchronized folder, so new files need no project edits. Constraints that come from the generated Swift code:
- Each mapped Go package is a Swift namespace (`WalkerVO`, `SemanticShapeVO` for package `semanticshape`, `SemanticScrapeVO`, `Walker` for package `service` with `Walker.ServiceClient`, `GoTime`; set in `go/goswiftrpc.yaml`), so the app always writes qualified names (`WalkerVO.ScrapeResult`). Extensions too: an unqualified `extension X` no longer finds the generated type.
- A zero `time.Time` is encoded as `null`, but a value `time.Time` becomes a non-optional `Date`. Use `*time.Time` for timestamps that can be unset (see `vo.ScrapeSummary`).
- go's `time.Duration` (nanoseconds) is `GoTime.Duration`; a bare `Duration` is `Swift.Duration`.
- The app has no graph view for now - the 3D graph was removed, the Go side (`GetGraph`, `GetPageGraph`, `GetPageFolderLinks`, `GetFolderPages`) stays and the generated Swift client still has those calls.
- The shape developer is the "Shapes" section of a server in the main window (`ShapeDevView` with its control bar instead of toolbar items, `ShapeDevModel` kept per server in `ServerModel.shapeDev`, so it survives switching sections; `ShapeWebView`) and iterates on a semantic shape against a live page. It calls `GetShapeRoot`/`ValidateShape`/`GetShapeRootVersion` (`service/shapeservice.go`; the app polls the version every second and validates again when a shape file changes), which load the shape root from a path on the server (client and server share a file system) and return an `semanticshape.TraceNode` tree (`Root.Trace`). Selecting a node highlights its locators in the WKWebView. A local server brings the shape root of its config, resolved against the config's directory, and its site (base url + first path) as the first page (`ShapeDevModel.follow`, every time the section opens; the shape root menu lists the config's root first, `configRoot`). Without a shape root the section shows only `ShapeRootPrompt`, which makes the user choose a folder; for a local server it is written to the config as `shaperoot` (`ServerStore.setShapeRoot`, relative to the config's directory when inside it). The group header sits next to the group picker (`GroupHeaderButton`): a local server keeps it in its config as `groupheader` (`ServerStore.setGroupHeader`, `follow` reads it back), for a remote one it is an override kept in the app; either way `ValidateShape` gets it as `groupHeader` (empty: the walker's own), so an edit counts before the walker restarts. The tree (`ShapeTreeView`) writes rules as plain-language chips, marks elements from other shape files (`Source`) and wildcards (`TraceNode.Via`), and shows the details of the selected node inline - neutral selection, a click on the selected row toggles the details, keyboard navigation is its own (List without selection binding). Source references open the editor chosen in the window's toolbar or the settings - one setting, `Editor.key` - at the line (`EditorMenu` greys out editors whose url scheme has no app, `SourceLink`, `zed://file…`, `vscode://file…`). The middle column (`PageDataView`) shows a link preview from the OpenGraph data (`OpenGraphView`), the head and the JSON-LD of the validated html (`semanticshape.ExtractPageData`, same locators as the trace), linked with the tree in both directions. The right column (`OutlinePane`, toolbar toggle, hidden by default) shows the semantic outline of the page from the same source as the validation - for "Rendered" the DOM snapshot goes to `GetSemanticDocument` as html, so selectors match the web view; it reloads with the page (`ShapeDevModel.pageVersion`) and the source, not with shape edits; the content of a branch comes from `ShapeDevModel.outlineContent()`, same source, and hovering highlights in the page via `ShapeHighlighter.highlight(locators:color:)`. The other way round, the selected shape node marks the outline (`SemanticOutline.marked` from `ShapeDevModel.selectedLocators`, same css path scheme as the selectors): the row of a locator, else the outermost rows inside it, else a weaker mark on the nearest visible row around it (a collapsed nav, a section around an image); the outline scrolls to the first mark. Clicking an outline element also selects it (`ShapeDevModel.selectOutline`, `outlineSelection`): one selection at a time - it deselects the shape node and a shape node clears it, a new outline too; the selection is highlighted in the page in the outline's purple and shown in the html pane, hovering returns to it. Under the web view (`VSplitView`, toolbar toggle `shapeDevShowsElementHTML`) `ElementHTMLPane` shows the elements of the selected shape node as indented html (`ShapeHighlighter.html(locators:)` serializes them from the web view's DOM without the highlight's class and style, at most 2000 lines; `HTMLHighlighter` colors it like `JSONHighlighter`).
- The app is **not sandboxed** (hardened runtime only): local walkers read configs and shape roots by path. The "helpers" run script phase builds `go/cmd/walker` and `go/cmd/configvalidator` (`go build -C "$ROOT/go"`) into `Contents/Helpers` (with the Go pinned in `mise.toml`, resolved via `mise which go` with `GOTOOLCHAIN=local` - the build fails if mise is missing or `mise trust && mise install` hasn't run; target `ENABLE_USER_SCRIPT_SANDBOXING = NO`, go needs its module cache).
- Configs are edited only in the main window, in the overview of a local server: `LocalConfigForm` is the config form (`ConfigFormView`, fields with notes on the resulting crawl behaviour - keep them in sync with the Go side) with the walker's state on top. It saves to the file right away and rereads it when it changes on disk. Its yaml backend is the `configvalidator` helper; `ConfigTool` talks to it over stdin/stdout JSON.
- Local walkers: a `Server` with a `configPath` is a local config (sidebar section "Local"), its `baseURL` follows the config's `addr` (`ServerStore.refreshLocal`, not while its walker runs). `LocalWalkers` (owned by the `AppDelegate`, which stops them on quit) runs the walker helper per config with `-exit-on-stdin-close`, in the config's directory, and keeps state and log (`LocalWalkers.logLines`, a setting, default 10000 lines). Local servers get the normal `ServerDetailView`; their `OverviewView` puts the scrape cards above the log (`LocalWalkerLogPane`) and the config form beside them.
- Live metrics (top of the Performance view, `LiveMetrics`, `LiveMetricsView`): the `AppDelegate` (owner of `ServerStore` and `LocalWalkers`) runs `ServerStore.sampleMetrics` for the app's lifetime: every refresh interval it reads the `/metrics` of all servers in parallel (local ones only while running, 5 s timeout) (`PromText` parses the text format) and keeps the charted series for 30 minutes in memory - a local debugging tool. Each `MetricsChart` is evaluated locally (rate, gauge, histogram quantile over bucket increases) and carries the equivalent PromQL, so a Prometheus server backend can answer the same charts later. Charts use one axis each; new metrics need a `kept` entry, a chart case and its PromQL.
- The result inspector (`ResultSections`, shared by the results, folder and broken link inspectors) shows the semantic outline of the whole page (`SemanticOutlineSection`, `SemanticOutline`) instead of the scraped headings - landmarks tinted, navs collapsed with their links, it loads without content; clicking an element shows the content of its branch - texts, teaser links, images with thumbnails, figures, lists with markers and tables as grids - and clicking again hides it (`SemanticOutline.branches`, an element without an entry follows its parent). The first click loads the document with content once, the rows come from it with the content hidden outside the open branches (`isContent`, links only on navs) - `TestExtractDocument_ContentKeepsTheOutline` guarantees that this gives exactly the outline without content: the server fetches the live page via `GetSemanticDocument`, the loader comes from the environment (`semanticDocumentLoader`, set in `ServerDetailView`). Hovering an element highlights it in the preview by its selector (`PreviewController.highlight`), headings the selector misses in the live DOM are found by level and text. Title, description, canonical and robots still come from the scrape result's `Structure`.
- The app target must not use `MainActor` default isolation (it would isolate the generated `Codable` conformances). App model classes are `@MainActor` explicitly.

**Logging.** Log messages go through `log/slog` with attributes (`slog.Info("scrape cycle completed", "pages", n)`), never `fmt.Print`/`log.Print`. `cmd/walker` sets the default logger: `-log-level debug|info|warn|error`, `-log-format text|json`, text on stderr by default. `fmt` is only for program output: CLI results and usage, reports, `configvalidator`'s stderr (the app shows it as is). The app's log view parses the slog text lines (`SlogEntry`), so keep walker's default format text.

**Other pieces.** `service/service.go` wraps the Walker with filtering and paging over results. `metrics` gives each Walker its own Prometheus registry (`metrics.New()`, `Handler()`). The loop only updates the few true counters, through the `crawler.Observer` that `metrics.Metrics` implements. All per-scrape metrics come from a collector (`Metrics.Collect(walker.GetStatuses)`) that derives them from `GetStatuses()` at scrape time, once per view, with `scrape="current"|"complete"`. Add new per-scrape metrics there, not as state in `scrapeloop`. `metrics/validationmetrics.go` aggregates shape validation reports for it. `vo/` holds the shared value objects (`Status`, `ScrapeResult`, `Structure`, `Validations`).
